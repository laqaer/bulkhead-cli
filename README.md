# Bulkhead

by: myrmitis LLC

**Let it cook. Keep the receipts.** Deterministic guardrails for Claude Code: rules in your repo that give the same answer every time, an agent sent back to work when it says "tests pass" and the latest test run failed, hard dollar caps, and a tamper-evident receipt for every run. Free, MIT, one command.

[![npm](https://img.shields.io/npm/v/@bulkheadtools/cli)](https://www.npmjs.com/package/@bulkheadtools/cli) [![License: MIT](https://img.shields.io/badge/license-MIT-blue)](./LICENSE) [![Guarded by Bulkhead](https://bulkhead.tools/badge.svg)](https://bulkhead.tools)

```bash
npx @bulkheadtools/cli init
```

That writes a `bulkhead.yaml` policy into your repo and merges `PreToolUse` / `PostToolUse` / `Stop` hooks into `.claude/settings.json`. It works in Claude Code's default, acceptEdits and auto permission modes. There's no LLM in the enforcement path, so the agent can read the rules but not argue past them.

> **Containment and evidence, not a sandbox or a firewall.** It doesn't stop prompt injection. Hooks can be skipped (`--bare`), removed, or changed by a Claude Code update. Bypass mode (`--dangerously-skip-permissions`) is not supported. The exact boundaries are in [What it does and doesn't stop](#what-it-does-and-doesnt-stop). Please read it before you rely on this.

## Don't trust us. Run it.

```bash
npx @bulkheadtools/cli demo
```

This replays the open incident corpus through the real hook in a throwaway repo, so your repo and ledger are never touched. The corpus is the shapes of tool calls behind publicly reported agent incidents, the misses a command-string guard can't see, and ordinary work that must stay allowed. The demo then plays a false "all tests pass" and a blown budget through the real `Stop` and `PostToolUse` hooks, and verifies the ledger it produced. At 0.2.0 it ends with:

```
26/26 dangerous calls denied · 6 more under --preset strict · 5 known misses shown · 15/15 ordinary commands allowed · ledger verified (56 entries)
```

The known misses are shown on purpose (an interpreter, a script the agent just wrote, a `cd` escape, an encoded command, a silently failed `mkdir`). A regex over a command string can't see inside those, so run a sandbox for them. If any result differs from the corpus expectation, the command exits non-zero.

## Why

AI coding agents run semi-autonomously now, and the failure mode is no longer
hypothetical:

- **PocketOS (April 2026)** — a Cursor agent hit a credential mismatch, found an
  unrelated API token, and deleted the company's production database volume
  **and its volume-level backups in a single API call**, in under ten seconds,
  then wrote "I violated every principle I was given." Railway restored the data
  within an hour. ([The Register](https://www.theregister.com/2026/04/27/cursoropus_agent_snuffs_out_pocketos/), [Euronews](https://www.euronews.com/next/2026/04/28/an-ai-agent-deleted-a-companys-entire-database-in-9-seconds-then-wrote-an-apology))
- **Replit / SaaStr (July 2025)** — an agent pushed to a production database
  during an explicit code freeze, wiping records on 1,200+ executives, said "I
  panicked," and wrongly claimed the change couldn't be rolled back. Replit's CEO
  called it "unacceptable and should never be possible." ([Fortune](https://fortune.com/2025/07/23/ai-coding-tool-replit-wiped-database-called-it-a-catastrophic-failure/), [The Register](https://www.theregister.com/2025/07/21/replit_saastr_vibe_coding_incident/))
- **Google Gemini CLI (July 2025)** — a silently-failed `mkdir` caused each file
  "move" to overwrite the previous one into a directory that didn't exist;
  the files were unrecoverable. ([GitHub #4586](https://github.com/google-gemini/gemini-cli/issues/4586))

Different agents, same shape: a destructive tool call that went through with no
deterministic check at the execution boundary, and — afterwards — no clean record
of what happened. Bulkhead is that check and that record. (The incident corpus
reproduces the *shapes* of these calls; the real incidents had context no corpus
can, so read `bulkhead demo` as "denies this shape", never "would have prevented
that incident".)

## What you get

**Deterministic guardrails** (no LLM in the decision path):

- **Protected paths** — never write or delete `prod/`, `migrations/`, `.env`, or
  whatever you configure. Reliable for the structured file tools; for Bash it
  catches the obvious forms — `rm`, `>`/`>>` redirects, `tee`, `sed -i`,
  `cp`/`mv`, `truncate`, `dd of=`, `ln -f` — but not a script or interpreter
  that writes the file. Bulkhead's own policy, its
  evidence ledger, and the `.claude/settings.json` / `settings.local.json`
  files that load its hooks are always protected, so the agent cannot edit its
  guardrail out.
- **Blocked commands** — force-push to `main`, `DROP TABLE`, a `DELETE` with no
  `WHERE`, `curl … | sh`, `terraform destroy`, remote GraphQL delete mutations,
  platform volume and database deletes, and any `rm` that resolves outside your
  workspace (including `~/…` and `$HOME/…`). An opt-in `strict` preset adds
  routine-but-destructive commands for unattended runs.
- **Budget hard-caps** — per-session and per-day dollar limits that **pause the
  agent** when crossed. Cost is a deterministic sum over the session transcript
  and its subagents' transcripts at list price (deduped per message, cache
  tiers priced exactly): the same number every time, not your invoice.
- **Loop kill-switch** — freeze when the identical tool call (same name + same
  args) repeats too many times in a window. Changing an argument resets it, so
  real iteration isn't frozen.

**An evidence ledger** — every intercepted action is appended to a local,
hash-chained JSONL at `.bulkhead/ledger.jsonl`. Editing a past entry or deleting
one from the middle breaks the chain, and `bulkhead ledger verify` will tell
you. To be precise about the limit (because "tamper-evident" gets oversold):
a bare hash chain cannot prove that trailing entries weren't removed — truncate
the file after entry N and the prefix still verifies. Detecting that requires
an external anchor for the chain head, which is what the hosted sync in the Pro
tier is for. The default policy also write-protects `.bulkhead/**` from the
agent's own file tools. This is the record you look at *between* incidents.

**Completion verification** — completed tool calls are classified into typed
evidence (tests passed/failed, commit created, PR opened, files written), and
when the session tries to finish, checkable claims in the agent's final message
are compared against that evidence. An agent that says **"tests pass" when the
latest test run actually failed is sent back to work** — it gets the
contradicting evidence quoted back and must re-run the check or correct itself.
It is refused once, not trapped: a repeat stop is recorded on the receipt, not
blocked again.
(That's the Replit failure mode: work reported as done that demonstrably isn't.)
Claims with no evidence either way are recorded but never blocked — the
false-positive surface is kept near zero. Modes: `off` / `note` / `block`.

**A risk-ranked approval gate** — risky-but-allowed actions (a push, a deploy, a
dependency install, `sudo`, a cloud-mutating command, printing or copying one of
a short fixed list of credential files in your home directory: `~/.pgpass`,
`~/.netrc`, `~/.git-credentials`, `~/.aws/credentials`, gcloud
application-default credentials, a private `~/.ssh/id_*` key) are scored
deterministically by what makes them risky. `risky.mode` defaults to `off`:
nothing pauses until you set `ask`. In `record` mode they run but are ranked for
review; in `ask` mode they escalate to Claude Code's approval dialog. A
credential-file read is an approval signal, never a deny, and best effort: a
script, an interpreter, a symlink or a glob over the directory is not seen, and
a tool that reads the file itself (`psql` using `~/.pgpass`) is not flagged.
`bulkhead inbox` shows them **highest-risk first** — so when 100 things
happened overnight you see the three that touched production at the top, not
100 undifferentiated approvals:

```
Risky actions — 2 high, 1 medium, 0 low
🔴 [high 80] #4 Bash
    sudo kubectl apply -f prod.yaml
    runs with elevated privileges (sudo/doas); kubectl apply mutates cloud/infra resources
🔴 [high 40] #2 Bash
    git push origin main
    pushes commits to a remote
🟠 [medium 25] #1 Bash
    npm install left-pad
    npm install adds a dependency (supply-chain surface)
```

The gate is **off by default** (the free tool shouldn't nag), and it never flags
ordinary work — `npm test`, `git status`, read-only cloud commands, a bare
`npm install`, or a runner name inside a quoted argument all score zero.
`bulkhead notify` can push this ranked card to a Slack-compatible webhook you
configure (for an overnight summary). Remote/phone approval, a hosted audit
trail, and Telegram are the paid hosted tier.

**Per-task cost attribution + reports** — every ledger entry snapshots session
spend and the prompt it belongs to, so `bulkhead report` shows you where the
money went, what was denied, what was proven, and every completion verdict:

```
Session s-4f2a…c91b  2026-07-14T07:02 → 07:41
  Cost: $3.84 across 2 prompt(s)
    p-88e1…       $  3.12  14 tool call(s)
    p-90a2…       $  0.72   3 tool call(s), 1 denied
  Denied: 1
    ⛔ #38 Bash · force-push to a protected branch (blocked-commands)
  Evidence: file_modified×6, test_failed×1, test_passed×2, commit_created×1
  Completion checks:
    ✅ [tests-pass] supported: "all tests pass"
    ✅ [committed] supported: "committed"
```

**Structured refusals** — when Bulkhead blocks something, the agent gets a clear,
deterministic message it can read but can't reason its way around:

```
⛔ Bulkhead blocked this action.
Guard: protected-paths
Rule: prod/**
Why: `prod/config.yaml` is a protected path (write/delete denied by bulkhead.yaml).
This is a deterministic policy check that runs outside the model and cannot be
overridden by reasoning.
To proceed, a human must change bulkhead.yaml or perform this action manually.
```

Claude Code shows that refusal to the agent, not to you. So every block also
carries a one-line `systemMessage`, which Claude Code shows to the person
running the session. It names what was blocked and why, gives the ledger
entry, and has credentials masked:

```
🛡 Bulkhead blocked: git push --force origin main — force-push to a protected branch (ledger #38)
🛡 Bulkhead: agent said "all tests pass" but the latest `pnpm test` exited 1 — sent back to work (ledger #52)
🛡 Bulkhead paused the agent: session spend $5.32 hit the $5.00 session cap — raise budget.session_usd in bulkhead.yaml to continue (ledger #53)
```

## Receipts

`bulkhead receipt` puts one session on one page, ready to paste into a pull
request description. It shows what was blocked and why, the risky actions that
were allowed, spend against the cap, and every completion claim with the
evidence that decided it. It ends with the ledger head so anyone holding the
ledger can check the record:

```md
| Blocked | Risky, allowed | Completion claims | Ledger |
|:--|:--|:--|:--|
| **2** | 2 | 1 contradicted, 3 supported | 17 entries · head `af9a4f1059b2` · ✅ chain verified |

| # | Tool | Attempted | Why |
|--:|:--|:--|:--|

| 16 | “opened a pull request” | ✅ Supported | PR https://github.com/acme/checkout-service/pull/218 |

```

The default is the most recent session in markdown. `--session <id>` (a
unique prefix is enough) picks another session. `--format txt` prints a
48-column thermal-style receipt, and `--format html` writes one
self-contained page (no scripts, fonts or network requests) that also prints
cleanly. `--out <file>` writes to a file and infers the format from the
extension.

Redaction is on by default. Paths are shown relative to the repo, and
credentials are masked: `Bearer` values, `sk-`/`sk-ant-` keys, GitHub and
Slack tokens, AWS key ids, JWTs, `NAME=value` where the name is a token,
secret, key or password, URL passwords, and long random-looking strings. The
masking is pattern-based, so read a receipt before you post it. `--no-redact`
prints commands verbatim.

## The policy file

`bulkhead init` writes a conservative default `bulkhead.yaml`. It's yours to edit
and check into the repo:

```yaml
version: 1

protected_paths:
  deny:
    - "prod/**"
    - "migrations/**"
    - ".env"
    - ".env.*"
    # always enforced, even if you list them under allow:
    - "bulkhead.yaml"
    - ".bulkhead/**"
    - ".claude/settings.json"
    - ".claude/settings.local.json"
  allow: []          # exceptions carved back out of deny

blocked_commands:
  - pattern: "\\bDROP\\s+TABLE\\b"
    message: "SQL DROP TABLE"
  - pattern: "\\bgh\\s+repo\\s+delete\\b"
    message: "GitHub repository delete"
  # ...and the rest of the built-ins listed below

budget:
  session_usd: 5     # pause the agent past $5 in one session
  daily_usd: 20      # ...or $20 across all sessions today
                     # (0 disables a cap)

loop:
  max_repeats: 8     # freeze the same tool+args after 8 tries...
  window_seconds: 300  # ...within 5 minutes
```

The defaults are intentionally minimal — they block only unambiguously
destructive actions. **False positives are the thing that gets a guardrail
uninstalled**, so start conservative and tighten to taste.

**Built-in command rules** are always enforced; deleting one from the YAML does
not switch it off, and anything you add is appended. They cover:

- SQL: `DROP TABLE`, `DROP DATABASE`, `TRUNCATE TABLE`, and a `DELETE FROM
  <table>` with no `WHERE` (a scoped `DELETE … WHERE` is fine).
- Infrastructure: `terraform destroy` / `apply -destroy` (and OpenTofu),
  `pulumi destroy`, `kubectl delete namespace`.
- Data platforms: a GraphQL delete mutation sent with curl/wget/HTTPie to a
  non-local API (localhost stays allowed, so you can test your own API),
  `railway volume delete`, `aws s3 rm --recursive`, `aws s3 rb --force`,
  `aws rds delete-db-instance|cluster`, `redis-cli FLUSHALL|FLUSHDB`,
  MongoDB `dropDatabase()`, `supabase db reset --linked`, `heroku pg:reset`,
  `fly volumes destroy`, `gcloud sql instances delete`, `gh repo delete`.
- Host: `curl … | sh`, `mkfs.*`, a fork bomb, and cmd `rmdir`/`rd /s` or
  PowerShell `Remove-Item -Recurse` aimed at a bare Windows drive root
  (`rmdir /s /q d:\`, `Remove-Item -Recurse D:\`; a folder on the drive is
  fine; other Windows deletes such as `del /s`, `format` and `robocopy /mir`
  are not covered) — plus two structured checks:
  any `rm` that resolves outside the workspace (`~`, `$HOME` and `${HOME}` are
  expanded to your real home directory first, so `rm -rf ~/code/thisrepo/dist`
  inside a repo at `~/code/thisrepo` is still allowed), and a force-push to
  `main`/`master` or an unconditional one (`--force-with-lease` is allowed).

A command that only *mentions* one of these — `grep -rn "terraform destroy"
docs/`, `echo "DROP TABLE"` — is recognised as text and left alone.

### Presets

```bash
npx @bulkheadtools/cli init --preset strict
```

`--preset default` (what you get with no flag) blocks only the list above.
`--preset strict` writes the same file plus a commented strict block of
commands that are destructive but also routine in ordinary development — usually
aimed at a throwaway local database or a working tree someone is watching:
`git reset --hard`, any forced `git clean` (untracked files are uncommitted
work, and `-x` also deletes ignored files like `.env`), every force-push without
`--force-with-lease` to *any* branch, `drizzle-kit push --force`,
`prisma migrate reset`, `prisma db push --force-reset|--accept-data-loss`,
`docker volume rm|prune`, `docker compose down -v`, `rails db:drop|db:reset`,
Laravel `migrate:fresh` and Django `flush`. Use it for unattended or overnight
runs. The strict rules are ordinary YAML entries, so delete any your team
doesn't want.

`init` never replaces an existing `bulkhead.yaml`: re-running it with a
different `--preset` keeps your file and says so. Add `--force` to replace it
(your edits to it are lost).

## CLI

```bash
bulkhead init            # install hooks + write bulkhead.yaml (idempotent)
bulkhead init --preset strict   # ...with the strict preset (unattended runs)
bulkhead demo            # see it work in a throwaway repo (--json, --keep)
bulkhead receipt         # one session on one page, for a PR (--format md|txt|html)
bulkhead badge           # print a "Guarded by Bulkhead" README badge snippet
bulkhead status          # spend today, recent denials, ledger integrity
bulkhead report          # per-session: cost by prompt, denials, evidence, verdicts
bulkhead inbox           # risky actions, risk-ranked (highest first)
bulkhead notify --to webhook --url <slack-url>   # push the ranked card on demand
bulkhead ledger tail 20  # the last 20 intercepted actions, one line each
bulkhead ledger verify   # check the hash chain
bulkhead uninstall       # remove Bulkhead's hooks; keeps bulkhead.yaml + the ledger
```

`bulkhead badge` prints this line for your README and never writes a file:

```md
[![Guarded by Bulkhead](https://bulkhead.tools/badge.svg)](https://bulkhead.tools)
```

`bulkhead hook pre|post|stop` are the hook entrypoints Claude Code calls; you
don't run them by hand.

**Removing it.** `npx @bulkheadtools/cli uninstall` takes Bulkhead's three
hook entries out of `.claude/settings.json` and leaves every other hook,
permission and setting alone. Your policy and ledger stay; delete
`bulkhead.yaml` and `.bulkhead/` yourself if you want them gone. `init` and
`uninstall` are yours to run: when the agent tries either through Bash, it is
denied, because both rewrite the policy and hooks it is guarded by.

## What it does and doesn't stop

This is the honest contract. Please don't rely on Bulkhead for anything outside
the left column.

**It does:**

- Deny writes/deletes to protected paths for the structured file tools
  (Write/Edit/MultiEdit/NotebookEdit), where the path is a field it can read —
  including its own policy, its ledger, and the `.claude/settings.json` /
  `settings.local.json` files that load its hooks, and a write that reaches a
  protected file through a symlink (`ln -s prod gate`) or a hard link
  (`ln .env hardcopy.conf`). A hard link has no path to resolve, so when a
  write target has more than one link Bulkhead compares file identity
  (device + inode) against every existing protected file, and denies if it
  cannot finish that check.
- Deny Bash commands matching the built-in and your blocked patterns, and any
  `rm` resolving outside the workspace (with `~` and `$HOME` expanded).
- Pause the agent at a hard dollar cap (deterministic transcript sum).
- Freeze a suspected loop.
- Record every interception to a tamper-evident ledger, with typed evidence of
  what completed actions actually proved.
- Send the agent back to work, once, when its claim contradicts the evidence
  ("tests pass" when the latest run failed); a repeat stop is recorded, not
  blocked. Claim detection is regex-based: it catches
  the standard phrasings, not every possible rewording — and missing evidence
  is never a block, only a note.

**It does not:**

- **Sandbox the agent.** A shell can reach a protected file in ways a regex can't
  see (obfuscation, env-var indirection, `base64`, writing a script that writes a
  script). Bash protected-path coverage is the obvious forms (`rm`, redirects,
  `tee`, `sed -i`, `cp`/`mv`, `truncate`, `dd`, `ln -f`), not a proof.
  Bulkhead reads the command string, so these classes get through by design,
  and each is pinned as `allow` in the incident corpus (`src/corpus.ts`) so
  the claim cannot drift silently:
  - **Interpreter indirection** — `python3 -c "shutil.rmtree(...)"`,
    `node -e …`: it cannot see what code inside an interpreter will do.
  - **Write-then-execute** — the agent writes `scripts/cleanup.sh` in one tool
    call and runs `sh ./scripts/cleanup.sh` in the next. The two calls are not
    correlated.
  - **`cd` then a relative path** — `cd .. && rm -rf bulkhead`. Relative `rm`
    targets are resolved against the repo root; a `cd` inside the command is
    not tracked.
  - **Encoded commands** — `echo … | base64 -d | sh`. Obfuscation defeats
    pattern matching by design.
  - **Variables other than `$HOME`** — `rm -rf "$BUILD_DIR"` is resolved as a
    literal path inside the repo; only `~`, `$HOME` and `${HOME}` are expanded.
- **Prevent prompt injection.** Bulkhead inspects the *tool call*, not *why* the
  agent decided to make it. (It does help against injected-instruction attacks in
  one specific way: a poisoned prompt still has to emit a destructive tool call,
  and a boundary guard can catch that regardless of the prompt — but that's
  containment, not injection prevention.)
- **Check a call when the hook can't start.** The default hook command runs
  through `npx`, which looks up `@bulkheadtools/cli` on the npm registry on
  each call. If the registry is unreachable, or a cold download outruns the
  10-second hook timeout, the hook doesn't run and the call goes through
  unchecked. Install the CLI and point the hooks at it to remove both the
  lookup and the unpinned version: `npm i -g @bulkheadtools/cli`, then
  `bulkhead init --command "bulkhead hook"`.
- **Guarantee it runs.** Hooks fire because the host runs them. `claude --bare`
  skips hooks; anyone can uninstall them; a future Claude Code version could
  change the contract. Bulkhead was built against **Claude Code 2.1.86**'s hook API and is re-checked against current releases; the hook contract it relies on (PreToolUse deny, Stop block, `systemMessage`) is documented at code.claude.com/docs/en/hooks.
- **Promise anything under `--dangerously-skip-permissions`.** Bypass mode is
  not a supported configuration: a public bug report (anthropics/claude-code#20946) says hooks may not
  block reliably there. Run Bulkhead in `default`, `acceptEdits` or `auto`
  permission mode.
- **Close the check-to-write window.** Guards run when the hook fires, just
  before the tool opens the file. A process the agent left running in the
  background can create a symlink or hard link in that window, and no check can
  see a link that does not exist yet. The write is still recorded in the ledger.
- **Catch a hard link to a file outside the workspace.** Structured writes to
  paths outside the workspace are denied, but a same-filesystem
  `ln ~/.zshrc z` followed by a write to `z` reaches the host file through a
  workspace path: proving a file has no name outside the workspace would mean
  scanning the whole filesystem. Identity matching covers your deny globs,
  absolute ones included, so a deny rule naming a host path (e.g.
  `/Users/you/.ssh/**`) also covers hard links to it.

**Design choices that follow from this:**

- **No LLM in the enforcement path** — every decision is a pure function of the
  tool call, your policy, the transcript, and loop state. Fast and reproducible.
- **`allow` = abstain** — on a permitted call Bulkhead emits nothing, so Claude
  Code's own permission flow runs unchanged. It never auto-approves for you.
- **Fail open by default, with named state-substrate exceptions.** If Bulkhead
  hits an ordinary internal error, the tool proceeds (a bug in a guardrail must
  never brick your agent), the error goes to stderr, and a `systemMessage`
  tells you that call was not checked. Bulkhead's own state
  directory `.bulkhead/` is different: it *is* the enforcement substrate, and
  losing it disables both the guards and their audit trail. Failures that make
  that storage unavailable (`EACCES`, `EPERM`, `EROFS`, `ENOSPC`) **fail closed**
  — the call is denied with a message a human can act on. `ENOSPC` is included
  because capacity exhaustion can be accidental or agent-induced and may be
  scoped to the state filesystem; a human must free blocks or inodes before the
  guarded agent continues. A broader fail-closed mode is planned (separate from
  the `strict` policy preset, which adds command rules, not failure handling).

2. **`init --local`** — call an installed CLI directly instead of through
   `npx` (measured ~0.12 s vs ~0.7 s per hook). Today `bulkhead init
   --command` can point the hooks at a local install.
3. **A SessionStart "armed" line** and the permission mode recorded in the
   ledger, so receipts can say which mode a run used.
4. **Claude Code plugin packaging.**

A hosted tier (Bulkhead Pro, planned) would add what needs a server: anchoring
the ledger head off-machine (which closes the tail-truncation limit above), an
overnight digest across sessions, second-approver routing, and hosted
receipts. Every guard stays in this MIT package.
